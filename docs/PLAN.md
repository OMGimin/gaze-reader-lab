# 기획과 기술 결정

확인일: 2026-10-22. 대상은 책상 앞 Mac 사용자이며, 웹툰을 읽을 때 손을 쉬게 하는 보조 수단이다. 첫 범위는 Mac Chrome 확장, 카메라 없는 모의 체험, 자체 제작한 긴 읽기 페이지다. 네이버 콘텐츠는 가져오지 않고 현재 페이지의 루트 스크롤 위치만 바꾼다. 실행에 계정·API 키·유료 서비스는 필요 없다. 공개 저장소에는 소스와 문서만 제공하며 웹 서비스는 배포하지 않는다.

## 사용자 경험과 합격 기준

| 상황 | 동작 |
|---|---|
| 시작 전 | 카메라 꺼짐, 자동 스크롤 잠김 |
| 보정 | 9점; 각 점 1.2초 시선 이동 후 새 표본 24개, 4.5초 안에 수집하지 못하면 해당 점 재시도 |
| 확인 | 별도 5점; 정규화 좌표 평균 오차 ≤0.10, 최대 ≤0.18, 위/중앙/아래 각 영역의 80% 이상 분류 일치 |
| 읽기 | 중앙 x=20~80%, y=30~70%에서 350ms 응시하면 한 번의 명령을 준비 |
| 넘기기 | x=20~80%, 아래 y≥86% 또는 위 y≤14%에서 900ms 연속 응시 |
| 이동량 | 뷰포트 높이의 55%, 최대 520px를 즉시 한 번 이동; 반복하려면 중앙 재응시 |
| 취소 | 다른 영역으로 시선을 옮기면 누적 응시 취소; Esc·정지·수동 스크롤·창 전환은 수동 재개 필요 |
| 추적 실패 | 얼굴 없음·다중 얼굴·잘못된 좌표는 정지; 새 프레임 300ms 이상 부재도 정지 |
| 깜박임 | 짧은 눈 감기는 누적 응시 취소·중앙 재준비; 250ms 이상 감으면 정지 |
| 변경 | 머리 위치·창 위치·크기·배율 변화는 보정 무효화 |
| 종료 | 영상 트랙 해제, 보정 데이터는 메모리에서 폐기 |

응시는 읽기 행동일 수도 있다. 따라서 조작 영역을 별도 띠로 표시하고 ‘중앙 준비 → 명령 띠 응시 → 한 번 이동’ 순서를 요구한다. 이 설계가 실제 오작동률을 낮추는지는 아직 가설이다. 모든 시간·범위·오차 기준은 초기 실험값이며 접근성 표준이나 임상적 기준이 아니다. 인위적으로 부드러운 긴 스크롤 애니메이션 대신 즉시 이동을 택해 정지 후 남은 이동이 없도록 했다.

## 기술 선택

| 대안 | 검토 결과 |
|---|---|
| MediaPipe Tasks Vision + 자체 보정 | 선택. npm 1.1.1 고정, Apache-2.0. 공식 1.1.1 릴리스는 2026-10-14로 유지보수 활동 확인. 얼굴·눈 특징 추출과 의도 판정을 분리하기 쉽다. |
| WebGazer | 실제 화면 응시 추정과 보정 회귀를 제공하는 유효한 대안. npm 3.5.3, GPL-3.0-or-later, 메타데이터 최종 수정 2026-02-24 확인. 폐기된 프로젝트로 판단하지 않았다. 이번에는 적은 상태와 명시적 보정·외부 통신 통제를 위해 직접 회귀를 구현했다. GPL 자체가 사용 불가 사유는 아니다. |
| 홍채 중심의 단순 임계값 | 화면 좌표·개인차·자세를 반영하지 못해 제외. |
| Apple 기본 기능 | iPhone/iPad의 Eye Tracking을 이미 사용할 수 있다면 먼저 비교할 대상. 이번 프로젝트의 차별점은 웹툰의 ‘한 구간 이동’, 중앙 재준비, 되돌림, 실패 시 정지에 특화한 UX다. 정확도가 더 높다고 주장하지 않는다. |

[MediaPipe 릴리스](https://github.com/google-ai-edge/mediapipe/releases/tag/v1.1.1), [Face Landmarker 공식 가이드](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker), [WebGazer 공식 저장소](https://github.com/brownhci/WebGazer).

Google도 홍채 추적만으로 사람이 어디를 보는지 알 수 없다고 명시한다. 눈꼬리 기준 홍채 상대 x/y 4개를 실제 영상 종횡비에 맞춘 단위로 추출한다. 점별 특징 중앙값과 이상치 검사를 거친 뒤 점마다 같은 가중치로 표준화 ridge 회귀를 맞춘다. 얼굴 중심·크기·코 상대 위치 5개는 별도 자세 변화 제한에만 사용한다. 작은 머리 움직임을 시선 신호로 학습하는 혼동을 막기 위해 회귀 입력에서는 제외했다. 회귀 결과는 정규화된 뷰포트 좌표 추정치이며 기하학적으로 보장되는 시선 광선이 아니다. 학습에 쓰지 않은 5점의 모든 유효 표본으로 오차와 실제 명령 영역 일치율을 확인하고, 실패한 모델은 적용하지 않는다. 확인 단계의 이상치를 제거하거나 통과 문턱을 낮추지 않는다. 실제 읽기에서 적용하는 EMA 평활화도 합격 판정에는 사용하지 않아 판정은 보수적이다. 범위 밖 예측은 화면 가장자리로 잘라 넣지 않고 정지한다. [Google의 홍채 추적 설명](https://research.google/blog/mediapipe-iris-real-time-iris-tracking-depth-estimation/).

Apple의 공식 Eye Tracking 안내는 iPhone/iPad에서 보정 후 시선으로 시스템을 조작하는 기능을 설명한다. Mac의 공식 Pointer Control 안내는 카메라로 얼굴·머리 움직임을 따르는 Head Pointer를 설명한다. 이를 같은 입력 방식으로 혼동하지 않는다. [iPhone Eye Tracking](https://support.apple.com/guide/iphone/control-iphone-with-the-movement-of-your-eyes-iph66057d0f6/ios), [Mac Head Pointer](https://support.apple.com/guide/mac-help/move-the-pointer-using-head-pointer-mchlb2d4782b/mac).

## 구조와 개인정보

```text
사용자 카메라 시작 버튼
  → 별도 확장 카메라 창의 video / MediaPipe CPU WASM
  → 수치 특징만 runtime Port
  → service worker의 단일 선택 탭 라우팅
  → content script의 보정 / 확인 / IntentGate
  → window.scrollBy (읽기 페이지)
```

카메라 창을 따로 두어 네이버 페이지의 카메라 권한이나 모델 로딩 CSP에 의존하지 않는다. 단, 이 구조의 실제 Chrome 확장 권한 흐름과 창 가림 시 성능은 사용자가 확인해야 한다. 카메라를 쓰지 않는 데모는 같은 Reader·IntentGate 코드를 사용한다.

카메라 원본은 영상 요소와 추론 메모리에만 존재한다. 네트워크 전송·녹화·파일 쓰기·localStorage·IndexedDB·사용자 식별을 하지 않는다. 수치 특징과 보정값도 영속 저장하지 않는다. MediaPipe의 일반 개인정보 안내에는 사용량 지표가 언급되어 있으므로, ‘라이브러리가 원래 절대 통신하지 않는다’고 가정하지 않는다. 런타임 CSP의 `connect-src 'self'`, 로컬 번들, 원격 호스트 권한 없음으로 외부 전송 경로를 막는다. 실제 모델 초기화와 빈 영상 추론에서 외부 요청 0건을 테스트했다. 네이버 사이트 자체의 기존 네트워크 요청을 차단하는 확장은 아니다.

## 구현·검증 순서와 남은 근거

안전 상태 머신과 회귀의 단위 테스트 → 로컬 원본 읽기 화면 → 확장 연결·카메라 수명 관리 → 실제 WASM 로드·빈 프레임 추론 → 합성 특징 기반 전체 보정 UI → 독립 코드 리뷰 → 수정·회귀 검증을 수행했다. 독립 리뷰에서 연결 종료 재귀와 명령 영역에 도달하지 못하는 보정 통과 사례를 수정했다.

남은 근거는 실제 사람의 시선 정확도, 10분 읽기 중 오작동률·피로, 안경/저조도/외부 모니터 조건, 실제 네이버 루트 스크롤 구조와 확장 설치·카메라 권한 흐름이다. 실제 보정이 반복 실패하면 임계값을 느슨하게 하기보다 WebGazer 또는 학습된 gaze 모델과 비교할 필요가 있다.
